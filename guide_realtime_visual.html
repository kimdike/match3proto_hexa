🎮 헥사 3매치 게임

— 그림으로 이해하는 게임 동작 원리 —

이 문서는 비개발자도 이해할 수 있도록 게임의 셀 구조, 블록 이동, 매칭, 충전 시스템을 그림과 비유로 설명합니다.

📌 한 가지만 기억하세요: 게임은 "데이터"와 "그림"을 따로 관리합니다. 그 두 가지가 서로 잘 맞춰져야 게임이 깨지지 않습니다.

🎯1. 게임판은 어떻게 생겼나?

이 게임의 판은 벌집 모양의 헥사그리드입니다. 6각형 셀들이 가지런히 놓여 있고, 한 셀의 이웃은 6방향(상·하·좌상·좌하·우상·우하)입니다.

크기와 패턴

총 77개의 셀로 구성. 좌→우로 컬럼 9개. 각 컬럼은 9-8-9-8-9-8-9-8-9 패턴으로 셀 개수가 번갈아 가며 배치돼 있습니다.

🐝 비유 — 벌집

꿀벌 벌집을 상상해보세요. 6각형 방들이 빼곡히 들어찬 모습. 우리 게임판도 똑같습니다. 한 방에서 옆으로 이동하면 좌상, 우상, 좌, 우, 좌하, 우하 — 총 6방향.

일반 셀 (블록이 있는 자리)
입구 (새 블록 등장 자리)
죽은 셀 (장벽)
통과 셀 (구멍)

위 그림은 실제 게임의 셀 배치를 그대로 표현한 것입니다. 위쪽 초록색 E 셀이 입구이고, 그 아래로 블록들이 떨어집니다.

🎨2. 셀에는 4가지 종류가 있다

같은 6각형 셀이지만 역할이 4가지로 나뉩니다. 게임 디자이너가 스테이지를 만들 때 골라 사용합니다.

🟢 entrance (입구) — 새 블록 생성 자리

맨 위에 9개가 기본 배치되어 있습니다. 아래 칸이 비면 새 블록을 떨어뜨립니다.

특이점: 보드 안에도 임의 위치에 추가 배치 가능. 그러면 그 셀 아래로 새 블록을 공급하는 또 다른 공급원이 됩니다.

⚫ normal — 일반 셀 (보통 블록이 있는 자리)

가장 흔한 셀. 블록이 머물고, 중력의 영향을 받아 아래로 떨어집니다. 매칭의 대상.

🔴 dead — 죽은 셀 (장벽)

블록이 절대 통과 못 하는 단단한 벽. 위에서 블록이 떨어지다 dead 셀 만나면 멈춥니다.

그 아래 빈 셀은 대각선에서만 채워집니다 (좌상→우하, 또는 우상→좌하).

🟣 pass — 통과 셀 (구멍)

블록이 머물지 않고 그냥 통과합니다. 굳이 비유하자면 구멍 뚫린 마룻바닥. 블록이 떨어지면서 그 위에서 안 멈추고 그냥 통과.

🔥3. 핵심 — 게임은 "두 개의 층"으로 만들어진다

⚠️ 이 섹션이 가장 중요합니다. 모든 race 버그의 원인이자, 모든 fix가 향하는 곳입니다.

게임 안에서 같은 셀에 대해 두 가지 정보를 따로 관리합니다:

📊 데이터 (board)

"이 셀에는 빨간 블록이 있다"
{ color: 빨강, type: normal }

게임의 진실. 점수 계산, 매치 감지 등 모든 로직의 기준.

↔️
🎨 그림 (blockEls)

화면에 실제로 보이는 빨간 원
<div class="hex-block red">

사용자가 보는 시각. CSS transition으로 부드럽게 움직임.

왜 두 층으로 나눠 관리하나?

데이터 변경은 즉시 처리해야 게임 로직(매치 감지, 점수 등)이 정확합니다. 하지만 그림은 부드럽게 천천히 움직여야 사용자 눈에 자연스럽게 보입니다.

예: 빨간 블록을 옆으로 옮기는 데이터 변경은 0.001초 안에 끝나지만, 화면 그림의 이동은 0.22초 동안 천천히 미끄러져 갑니다.

🏨 비유 — 호텔 객실 명부와 손님

명부 (데이터): "302호 손님은 김씨"라고 글로 적힌 기록. 즉시 수정 가능.

손님 (그림): 실제 호텔 안을 걸어다니는 사람. 302호에서 305호로 옮기려면 짐 챙기고 걸어가는 시간 필요.

명부는 즉시 "302→305 이동" 표시. 손님은 천천히 이동. 이 두 가지가 잘 맞아야 호텔이 잘 돌아갑니다.

3D로 시각화

아래 그림에서 파란색 평면이 데이터 층, 노란색 평면이 그림 층입니다. 두 층이 z축으로 분리된 모습.

📊 데이터 층 (board)
🎨 그림 층 (blockEls)

두 층이 어긋날 때 = 버그

"명부엔 김씨가 302호인데 실제로 김씨가 305호에서 자고 있다"면? 호텔은 혼란. 마찬가지로:

❌ ZOMBIE 상태

데이터: "여기 빨간 블록 있어"

그림: 없음

→ 사용자 눈에는 빈 셀로 보임

❌ DOM-DUP 상태

데이터: "여기 빨간 블록 있어" (1개)

그림: 빨간 원 2개

→ 사용자 눈에는 블록 겹침

🔄4. 블록을 바꾼다 (swap)

사용자가 두 인접한 블록을 손가락으로 드래그해서 위치를 바꾸는 동작이 swap입니다. 게임의 가장 기본 조작.

swap의 두 가지 처리 방식 비교

❌ 이전 방식 (race 발생)

  1. swap 시작 — el1, el2 잡음
  2. "옮길게~" 그림 transition 0.22초 시작
  3. 0.22초 후 명부(데이터) 갱신

⚠️ 그 0.22초 사이에 다른 작업자가 명부를 만지면 충돌

✅ 새 방식 (atomic, race 0)

  1. swap 시작 — el1, el2 잡음
  2. 명부(데이터) 즉시 갱신 ⚡
  3. 그림 transition 0.22초는 시각 효과만 진행

✓ 다른 작업자가 명부 봐도 이미 갱신된 상태

🏢 비유 — 엘리베이터를 옆 건물로 옮기는 작업

이전: "옆 건물로 옮길 거야~" 예약만 하고, 22초 후 실제 처리. 그 사이 엘리베이터 위치를 또 옮기려는 사람이 있으면 충돌.

이후: "옮긴 걸로 친다!" 즉시 장부에 기록. 시각적인 이동은 22초 동안 천천히. 누가 끼어들어도 이미 처리된 상태이므로 안전.

실제로 시연해보기

아래 보드에서 (가운데 블록)과 (오른쪽 블록)이 swap됩니다. 시작 즉시 데이터는 변경, 그림은 천천히 이동.

💥5. 매치 + 충전 — 블록이 터지고 새로 떨어진다

같은 색 블록 3개 이상이 한 줄로 모이면 매치가 일어나 그 블록들이 사라지고, 위에서 새 블록이 떨어져 빈 자리를 채웁니다.

1매치 감지 + 블록 제거

매치가 일어나면:

  • 데이터에서 즉시 분리: "이 셀엔 이제 블록 없음"
  • 그림은 matched 애니메이션(0.28초 동안 커졌다 작아지며 fade-out)
  • 애니메이션 끝나면 자동으로 DOM에서 제거

🎈 비유 — 풍선 터뜨리기

"이 풍선은 터졌다"고 즉시 기록(데이터). 화면에서 풍선이 빵! 하고 터지는 애니메이션은 0.28초 동안 진행. 끝나면 풍선이 화면에서 사라짐.

중요: "터졌다"는 기록은 즉시. "빵!" 애니메이션은 천천히. 두 작업이 독립적.

2중력 (Gravity)

매치된 자리가 비면 그 위에 있던 블록들이 아래로 떨어집니다. 진짜 중력처럼.

3충전 (Fill)

맨 위 비어있는 자리에 입구(entrance)에서 새 블록을 만들어 떨어뜨립니다. 한 컬럼에 빈 셀이 여러 개면 동시에 위에서 차례로 채워집니다.

4Ticker — 백그라운드 자동 검사

이 모든 일은 ticker라는 백그라운드 시스템이 매 0.05초마다 돌면서 자동 처리합니다.

0.00s — 빈 셀 검사
→
0.05s — 중력 1단계
→
0.10s — 충전 1단계
→
0.15s — 중력 2단계
→
...

💡 이 덕분에 폭발이나 매치가 일어나는 동안에도 충전이 백그라운드에서 동시 진행. 흐름이 끊기지 않습니다.

실제로 시연해보기

아래 보드의 가운데 컬럼 파란색 3매치가 터지고, 세 개의 새 블록이 동시에 위에서 떨어집니다.

⚡6. 동시에 두 곳에서 매칭하면? — 실시간 매칭

이 게임은 첫 매치가 진행되는 중에도 다른 위치에서 새 swap을 받습니다. 두 매치가 시각적으로 겹쳐 동시 진행됩니다.

왜 어려운가?

같은 셀에 두 작업이 동시에 일어나면 충돌(race)이 발생합니다.

예: A 흐름이 (3,5)의 빨간 블록을 매치로 터뜨리는 도중에, B 흐름이 같은 (3,5)에 새 블록을 swap해 넣으려 하면? 데이터와 그림이 어긋날 위험.

해결책 — 두 가지 메커니즘

① Lock 시스템

현재 처리 중인 셀(swap 두 셀 + 매치 라인 셀)에 "공사 중" 표시를 붙입니다. 다른 작업자가 그 셀에 swap 시도하면 거절됨.

🚧 비유 — 공사 현장

건물 한 곳에서 공사 중일 때 그 영역은 펜스로 막아둡니다. 다른 작업자는 다른 영역에서 자기 작업 가능. 공사 끝나면 펜스 해제.

게임도 똑같이 swap 영역과 매치 라인을 임시 lock. 끝나면 자동 해제.

② Atomic 처리

swap을 시작하는 그 순간 데이터를 즉시 변경. 그 후 시각 효과는 천천히 진행되더라도 데이터는 이미 안전.

③ 안전망

만에 하나 어긋나는 일이 발생하면 ticker가 매 0.05초마다 검사해 자동 복구. (다음 섹션 참고)

🛡️7. 실수해도 알아서 복구 — 안전망 시스템

완벽한 race 차단은 불가능합니다. 그래서 ticker가 매 0.05초마다 보드를 검사하면서 두 가지 문제를 자동 복구합니다.

안전망 1: ZOMBIE-RECOVER

ZOMBIE 상태: 데이터엔 블록 있는데 그림만 사라진 경우

📊 board[2][7] = { color: 빨강 } ← 있음

🎨 blockEls[2][7] = null ← 없음

→ 사용자 눈에는 빈 셀

복구 방법

ticker가 매 0.05초 검사 → ZOMBIE 발견 → 데이터에 기록된 색 그대로 새 그림을 다시 그립니다.

💡 핵심: 랜덤 새 블록이 아니라 원래 있어야 할 그 블록이 그대로 복구됩니다. 게임 진행에 전혀 영향 없음 (점수/매치/콤보 무관).

🎨 비유 — 그림 자동 복원

"이 자리에 빨간 사과를 그렸어"라는 기록(데이터)은 있는데 어쩐 일로 그림(시각)이 지워졌다면? 그림 복원사가 와서 기록을 보고 똑같은 빨간 사과를 다시 그려줍니다. 원본과 다르지 않게.

실제로 시연해보기

아래 보드의 가운데 블록 그림을 강제로 지워봅니다. 그러면 빈 셀이 됩니다. 그 후 "복구" 버튼을 누르면 자동으로 같은 색의 같은 블록이 다시 나타납니다.

안전망 2: DOM-DUP-CLEAR

DOM-DUP 상태: 같은 셀에 그림이 2개 겹쳐 있는 경우

📊 board[2][7]이 가리키는 그림 1개 + orphan(고아) 그림 1개

→ 사용자 눈에는 블록 겹침

ticker가 검사하다 같은 셀에 그림 2개 발견 → 데이터가 가리키는 진짜 그림은 보호, 다른 가짜(orphan)는 즉시 제거.

단, 매치 애니메이션 중인 그림(matched 클래스)은 보호합니다. 그건 자기 페이스로 사라질 예정이므로.

👥 비유 — 도플갱어 솎아내기

한 사람 자리에 똑같이 생긴 사람이 두 명 서 있으면 신분증(blockEls reference)을 가진 진짜는 두고, 가짜는 즉시 보내버립니다.

🏆8. 전체 정리 — 4가지 핵심 메커니즘

이 게임이 두 swap을 동시에 받으면서도 안 깨지는 이유는 다음 4가지가 동시 작동하기 때문입니다.

① swap atomic

swap 시작 시점에 데이터 즉시 갱신. 시각 효과는 별도 진행.

→ 220ms race 시간 0

② animationend detach

매치 블록은 데이터 즉시 분리. 그림은 애니메이션 끝나면 자연 사라짐.

→ 200ms race 시간 0

③ ZOMBIE-RECOVER

데이터엔 블록 있는데 그림만 사라지면 ticker가 자동 복구.

→ 빈 셀 안전망

④ DOM-DUP-CLEAR

한 자리에 그림 2개면 진짜만 두고 가짜 자동 제거.

→ 블록 겹침 안전망

✨ 결과

사용자 체감: 두 swap이 시각적으로 겹쳐 동시 진행됨 + 충전도 끊김 없이 부드러움 + 어떤 이상한 상황이 발생해도 0.05초 안에 자동 복구되어 사용자가 이상을 인지하지 못함.

개발자 체감: race 발생 시점 자체가 거의 0으로 줄어들고, 발생하더라도 안전망으로 자동 복구되므로 시각/게임 로직 모두 안정적.

"데이터 변경은 즉시, 시각 효과는 천천히. 그 두 가지가 어긋나도 ticker가 알아서 동기화한다."

— 이 게임의 핵심 철학
